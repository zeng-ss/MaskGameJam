## Addressables 远程加载失败排查（CheckForCatalogUpdates）

用户报错：

```
RemoteProviderException : TextDataProvider : unable to load from url :
  http://10.136.9.147:8090/StandaloneWindows64//catalog_0.1.hash
UnityWebRequest result : ConnectionError : Cannot connect to destination host
```

### 实测结论（我实际跑了网络诊断）

- `curl --noproxy '*' http://10.136.9.147:8090/` → 2 秒超时，连不上
- `curl --noproxy '*' http://127.0.0.1:8090/` → **同样连不上**
- `netstat -ano | grep :8090` → **本机没有任何进程监听 8090**
  → 结论：**目标地址上根本没有 HTTP 服务在运行**

- 另外发现**配置与报错不一致**：
  - `AddressableAssetSettings.asset` 里 Profile「Main」的
    `Remote.LoadPath = http://10.136.9.147/StandaloneWindows64`（**无端口**）
  - 但报错 URL 带 `:8090`
  - → 说明**运行的 catalog 是旧配置烘焙出来的**（改过 Profile 但没重新 Build）

（注：`curl` 不加 `--noproxy` 时返回 502 且 0.0008s 即回，是本机代理挡下的，与 Unity 的失败原因不同，别混淆。）

### 关键知识点（以后还会遇到）

1. **`Remote.LoadPath` 在 Build 时被烘焙进 catalog**。改完必须
   `Addressables > Build > New Build > Default Build Script` 才生效 ——
   **只改 Profile 不重新构建 = 无效**，这几乎是最容易踩的坑。
2. **默认 Profile 的 LoadPath 是 `http://[PrivateIpAddress]:[HostingServicePort]`**
   （HostingServicePort 默认 **8090**），需要 `Addressables > Hosting` 里 **Enable** 才有服务；
   **每次重启 Unity 后 Hosting 不会自动开启**。
3. **`Remote.BuildPath = ServerData/[BuildTarget]`**，所以静态服务器的根目录应当是 `ServerData/`，
   URL 形如 `http://<host>:<port>/StandaloneWindows64/catalog_0.1.hash`。
4. **URL 里的双斜杠 `//`** 来自 LoadPath 结尾多写的 `/`；LoadPath 用 `[BuildTarget]` 结尾即可避免。
5. **开发阶段最省事**：Play Mode Script 切成 `Use Asset Database (fastest)`，完全不碰远程服务器。

### 产出

- 新增 `Tools/启动Addressables服务器.bat`：
  双击即用 `python -m http.server 8090 --bind 0.0.0.0 --directory ServerData` 起本地服务器，
  并自动打印本机 IPv4（方便填进 `Remote.LoadPath`）。

## 编辑器卡死排查（点「endless」开始游戏后 Unity 无响应）

### 根因
`Assets/Scripts/AOT/HotUpdateSystem.cs:322` 原本是：

```csharp
Addressables.InstantiateAsync(GameLanuchKey).WaitForCompletion();
```

- `GameLanuch` 预制体位于**远程组**（实测：`ServerData/` 下 12 个组里除了
  `AOT` / `Built In Data` / `Default Local Group`，其余 9 个组都是远程组）
- `WaitForCompletion()` 会**同步阻塞主线程**直到 bundle 加载完成；
  远程服务器连不上时主线程就一直等 → **编辑器整个卡死，点哪都没反应**

**日志证据**：`Logs/Editor-prev.log` 尾部堆栈停在
`BundledAssetProvider/InternalOp:WaitForCompletionHandler` → `HotUpdateSystem:GameLanuch()`（:322）。
（另外：`Editor.log` 被重启覆盖了，卡死前的记录要看 `Editor-prev.log`。）

### 修复
- `GameLanuch()` → 改成协程 `GameLanuchCoroutine()`，用
  `yield return Addressables.InstantiateAsync(GameLanuchKey)`
- 调用点 `HotUpdate()` 里 `GameLanuch();` → `yield return GameLanuchCoroutine();`
- **零副作用**：原 `WaitForCompletion()` 之后没有任何代码，改异步行为等价，只是不再冻结主线程

### 遗留的同类隐患（本次未改，都是「有热更窗口」分支才走）
- `:259` 热更新窗口实例化、`:331`/`:344` `GetVersionInfo`/`GetVersion` 里的 `WaitForCompletion`
- `XLuaManager.cs:90` 的 `WaitForCompletion` **不能改成异步**：xLua 的 `CustomLoader`
  委托签名要求**同步返回 byte[]**；好在 `LoadLuaScripts` 里已先 `DownloadDependenciesAsync` 过，
  正常情况下读的是本地缓存

### 给用户的立即方案
Play Mode Script 切 `Use Asset Database (fastest)` → 完全不碰 bundle 和远程服务器，
开发期不会卡；要验证远程流程时再启动 `Tools/启动Addressables服务器.bat`。

## 点 endless 开始游戏卡死（真正原因：575 个对象池实例的 Lua 绑定开销）

### 现象
点 StartPanel 的 endless 按钮 → `SceneMgr.LoadSceneAsync("EndlessScene")` → **Unity 编辑器假死**
（不是报错，是彻底无响应）。用户强调「就是加载场景的时候卡死」。

### 根因（两层叠加）
1. `EnemySpawner:start` → `preload_all_pools()` 一次要实例化 **575 个**对象：
   `Cow30 + RedWarn30 + Explo15 + StarFish30 + BlueSlime30 + MultiBullet100 + MultiRobot30
   + HitPlayerBlood20 + SingleBullet100 + TurtleShell30 + SingleRobot30 + PlayerBullet100
   + ParabolicBullet30`
2. `LuaBinding.Bind` 每次绑定都用 `DoString` **编译一遍 Lua 源码** —— 这是最致命的一环。
3. 在 `Use Asset Database` 模式下 Addressables 的加载是**同步完成**的，
   于是 575 次 `Instantiate` + 575 次 `DoString` 全部挤在**同一帧**执行 → 主线程堵死几十秒。

**日志证据**：`Editor-prev.log` 尾部堆栈为
`Instantiate → LuaBehaviour.Awake → LuaBinding.Awake`，且日志停在 StartScene 加载完成之后
（没有出现 EndlessScene 的 `Loaded scene`），全程无报错 —— 典型的「同步阻塞」而非死循环。

> 为什么原来 C# 版本不卡：那时只有 Instantiate，没有 Lua 绑定开销。

### 修复
1. **`LuaBinding.cs`**：新增 `s_factoryCache` + `GetOrCreateFactory()`，
   把「每次 Bind 都 DoString 编译」改为「require + 取工厂函数**只做一次**，
   之后每次绑定只是一次 `factory.Call(owner)`」；`DisposeAll()` 里统一 Dispose 并清空缓存；
   同时不再创建无用的 `_scriptEnv`（几百个实例的 NewTable 开销）。
2. **`enemy_spawner.lua`**：预加载改成**分帧**——
   `preload_all_pools` 把 13 种资源展平成一条队列，`update_preload` 每帧只处理
   `PRELOAD_PER_FRAME = 20` 个，全部完成后才 `open_timer_panel()`（与原时序一致）；
   删除已无用的 `preload_enemy`。575 个约 29 帧 ≈ 半秒加载完，界面全程可响应。

### 新增工具
`Tools/lua_check.js` —— luaparse 批量校验 `Assets/LuaScripts/**/*.lua.txt` 的语法。
改完 Lua 先跑它，能在打开 Unity 之前发现语法错误。
（原先的校验脚本放在 `Temp/` 被 Unity 清理掉了，这次移到 `Tools/` 持久保存。）

## 「热更窗口没加载出来」的解答 + 修掉一个我引入的真 bug

### 为什么看不到热更窗口（设计如此，不是坏了）
`HotUpdateSystem` 里窗口只在**两个条件同时成立**时才被创建：
1. `CheckForCatalogUpdates` 发现远程 catalog 的 hash 与本地不同；
2. `GetDownloadSizeAsync > 0`（新 catalog 引用的 bundle 不在本地缓存里）。
调用链：`UpdateCatalogs → GetDownloadSize(keys) → downloadSize > 0 → PriorityHotUpdate()（建窗口）
→ _hotUpdateWindow.Show(...)`。
用户的日志里明确是 `无需更新 - catalog已是最新版本` → `catalogResult.Count == 0` → 整条下载分支被跳过
→ `_hotUpdateWindow` 始终 null → `HotUpdate()` 直接 `GameLanuchCoroutine()` 进游戏。
编辑器 Play 基本看不到：`Use Asset Database` 不走 bundle；`Use Existing Build` 时本地 catalog
就是刚构建的那份，与服务器一致。
想看到：① 真热更流程（打客户端 exe → 改东西重建 → 新 ServerData 推到服务器 → 运行**客户端**）；
② 勾新加的 `HotUpdateSystem.debugForceHotUpdateWindow`。
窗口 `OnEnd` 回调 = 「进度走满后出现的『进入游戏』按钮」被点击时才触发（见 `HotUpdateWindow.Update()`）。

### 🔴 修掉一个我上次改动引入的 bug（正好在这条路径上）
`_hotUpdateWindow.Show(downloadSize, () => { GameLanuchCoroutine(); });`
—— `GameLanuchCoroutine()` 返回 `IEnumerator`，**当语句调用等于创建出枚举器立刻丢掉，协程不执行，且 Unity 不报错**。
原始代码是 `Show(downloadSize, GameLanuch)`（那时 `GameLanuch` 是 void 方法，方法组可直接当 `Action` 传），
我上次改成协程时漏了 `StartCoroutine`。后果：**真热更下载到 100%、点「进入游戏」→ 游戏永远不启动**。
已改成 `StartCoroutine(GameLanuchCoroutine())`。

### 顺手清掉启动链路里最后的 `WaitForCompletion`
1. **热更窗口的实例化**（`PriorityHotUpdate`）：原来是 `InstantiateAsync(...).WaitForCompletion()`，
   而热更窗口恰恰是「远程不通时最该显示出来」的 UI，这一步会把编辑器整个卡死 → 改异步 + 失败打日志。
2. **`VersionInfo` / `Version` 的读取**：这两个资源在**远程组 HotUpdate** 里，原来用
   `LoadAssetAsync(...).WaitForCompletion()`。同步等待期间主线程不回主循环，而 bundle 下载要靠主循环推进，
   存在「等一个永远不会完成的操作」的死锁风险 → 改成协程 `LoadVersionInfo()`，结果存
   `_cachedVersionInfo` / `_cachedVersion`，读不到显示"未知"。旧的 `GetVersionInfo()/GetVersion()` 已删除。
现在 `HotUpdateSystem.cs` 里**已无任何真实 `WaitForCompletion`**（只剩注释）。

## `invalid arguments to openPanelByName` —— 点号写成了冒号

用户自己在 `esc_panel.lua:61` 的 `back_click` 里加了「暂停时点返回 → 弹 TipPanel 提示」，
报 `LuaException: invalid arguments to openPanelByName`（`[C]: in field 'openPanelByName'`）。

**根因：`UIManager.Instance.openPanelByName(...)` 用了点号，C# 实例方法必须用冒号。**
xLua 里 C# 实例方法**第一个参数就是 self（C# 对象本身）**，`obj:foo(a)` ≡ `obj.foo(obj, a)`；
写成点号时 Lua 不补 self → `"TipPanel"` 被当成 self、匿名函数被当成 `panelName` → 参数类型对不上。
对照：同一个方法在 `start_panel.lua:51` 用的是 `:`，所以那边一直正常。

**报错来源辨别**（`MethodWarpsCache.cs:307`）：不带 `!`、名字不带命名空间 = **反射**调用报的
（`UIManager` 没进 `LuaCallCSharp`，所以走反射）；生成代码报的长这样：
`invalid arguments to UnityEngine.Screen.SetResolution!`（`CodeEmit.cs:1558/1904`）。

已修 `esc_panel.lua:61`（`.openPanelByName(` → `:openPanelByName(`），并在 j 附近加了注释说明。
**全量扫过其它 Lua**：`.Instance.method(` 只剩注释里出现，`transform.method(` 也只剩注释，没有第二处。

顺手把这条补进 `Docs/Lua热更上手指南.md` 的「坑 11」（含 6 行判断口诀对照表），
虽然第 7.1 节对照表里本来就写了「调用实例方法用冒号」，但报错特征值得单独成条。
